# 跑步 WebGIS：项目规划与功能设计

## 1. 项目定位

这是一个面向个人跑步训练的 WebGIS：将运动手表导出的 FIT 轨迹转化为可查询、可回放、可分析的时空运动数据，并在地图与图表中呈现。

项目目标不只是展示跑步轨迹，而是回答三个实际问题：

- 我最近的训练量、强度和规律如何？
- 我在同一路线或相似强度下是否进步？
- 位置、坡度、配速、心率和跑姿之间有什么关系？

当前数据位于 `data/running/exportfrom20260806/`，其中有约 576 个 FIT 文件。抽样结果表明，记录中可用字段包括逐点经纬度、时间、距离、心率、速度/配速、海拔、步频、步幅、功率，以及部分跑姿指标。

## 2. 推荐技术路线

### 前端

- Vue 3 + TypeScript：页面结构、组件和类型约束。
- Element Plus：日期选择、筛选器、表格、抽屉和统计卡片。
- Leaflet：轨迹、热力图、起终点、公里标记、图层控制和地图交互。
- ECharts：日历、趋势图、折线图、散点图、柱状图和联动图表。

### 后端与数据处理

第一阶段推荐使用 Python，而不是立即引入 Spring Boot：

- Python 可直接使用 `fitparse`/`fitdecode` 解析 FIT。
- GeoPandas、Shapely、PyProj、GDAL/OGR 等库更适合轨迹空间分析、投影转换、缓冲区、空间叠加和导出 GeoJSON。
- Pandas 适合聚合每日、每周、每月训练数据并计算训练指标。
- FastAPI 很适合提供轻量 REST API，并自动生成接口文档；若暂时不需要动态接口，也可先由 Python 输出静态 JSON。

Spring Boot 并非不能做 GIS：可搭配 JTS、GeoTools、PostGIS 等，但 FIT 解析和数据分析生态不如 Python 顺手，学习成本也更高。若未来需要多用户、权限、复杂事务、稳定的企业级后台，可以保留将 API 层迁移或扩展为 Spring Boot 的空间。

### 推荐的渐进式架构

```text
FIT 原始文件
  → Python 导入与质量检查
  → 处理后的活动摘要 JSON + 单次轨迹 GeoJSON/JSON
  → FastAPI 查询接口（第二阶段，可选）
  → Vue 3 + Leaflet + ECharts
```

不要让浏览器或后端接口在每次请求时重新解析 FIT 文件。导入时预处理一次，访问时读取轻量化结果，性能和代码结构都会更好。

## 3. 建议目录组织

```text
webgis_for_running/
├─ data/
│  ├─ raw/                       # 原始 FIT，永不修改
│  ├─ processed/
│  │  ├─ activities.json          # 活动摘要索引
│  │  ├─ calendar.json            # 按日聚合的日历数据
│  │  ├─ invalid-files.json       # 无法解析或质量异常的文件
│  │  └─ tracks/                  # 每次活动一个 GeoJSON/JSON
│  └─ running/                    # 当前已有导出数据
├─ scripts/
│  ├─ import_fit.py               # FIT → 标准数据
│  ├─ build_summary.py             # 聚合统计、训练指标
│  └─ spatial_analysis.py          # 热点、路线相似度等 GIS 分析
├─ backend/                        # FastAPI（后续建立）
├─ frontend/                       # Vue 3（后续建立）
└─ 项目规划与功能设计.md
```

建议每次活动保存两层数据：

- `activities.json`：ID、日期、运动类型、距离、时长、平均/最大心率、平均配速、爬升、轨迹文件路径、标签和数据质量状态。
- `tracks/<id>.geojson` 或 JSON：逐点时间、经纬度、累计距离、心率、配速、海拔、步频、功率等。

这样既不需要立即使用数据库，也为未来迁移 SQLite、PostgreSQL 或 PostGIS 留下清晰的结构。

## 5. 最值得做的训练与空间分析

### 5.1 心率漂移

在配速近似时，比较活动前半程和后半程的心率。若后半程心率明显上升，可能反映疲劳、温度影响、补给不足或当前有氧耐力不足。

实现思路：过滤停顿点；按累计距离将活动切为前后两半；在相近配速区间内比较平均心率，并输出漂移比例。结果必须作为训练观察，而不是医疗结论。

### 5.2 配速稳定性与训练类型识别

通过每公里或固定时间窗的配速标准差，区分匀速跑、间歇跑和明显掉速的训练。

实现思路：计算 30 秒窗口、每公里窗口的配速均值与标准差；结合静止/低速时间和心率曲线，自动提供“可能为间歇训练”等建议标签，保留用户手工修改权。

### 5.3 坡度对表现的影响

轨迹的海拔和距离可推算局部坡度，并与配速、心率和功率一起分析。

实现思路：先平滑海拔，避免 GPS 高程噪声；按 50–100 m 计算坡度；以坡度分组展示平均配速、心率和功率。地图上以颜色标注上坡、下坡和平路。

### 5.4 训练负荷变化

重点不是用一个绝对阈值评价训练，而是与自己的近期训练基线比较。

实现思路：计算每日距离、时长和简化强度分数（例如时长 × 心率区间权重）；生成滚动 7 日和 28 日曲线；当短期负荷相较长期基线增加过快时提示注意恢复。

### 5.5 路线重合度与同路线进步

把多次跑过的相似路线归组，避免把上坡路线与平路路线直接比较。

实现思路：统一投影到米制坐标；对轨迹降采样；计算起终点距离、缓冲区重叠率或 Hausdorff 距离；满足阈值时归为同一路线。按距离对齐后比较配速、心率和海拔剖面。

### 5.6 空间探索度

这是很有 GIS 特色、且比总里程更有趣的指标：统计自己跑步到达过的空间范围和新区域。

实现思路：将所有轨迹投影后划分固定网格（如 250 m × 250 m）；统计每个网格首次到达时间、到达次数、累计距离；用分级设色图展示探索范围和重复跑区。

## 6. 数据质量与隐私规则

- 原始 FIT 文件只读保存，解析失败时写入 `invalid-files.json`，不能阻断其余文件导入。
- 单独处理非 running 的记录、距离为 0 的训练和无 GPS 记录，避免污染跑步统计。
- 对 GPS 跳点、停顿和异常速度进行标记或过滤，但始终保留原始值。
- 轨迹会暴露住址、学校等敏感地点。若未来公开部署，应支持起终点隐去、轨迹模糊化和私有数据访问控制。

## 7. 推荐实施顺序

1. 建立 Python 导入脚本：批量解析 FIT，输出活动摘要和单次 GeoJSON。
2. 建立 Vue 首页：运动日历、总距离/时长统计、活动列表。
3. 完成活动详情页：Leaflet 轨迹、时间回放、配速/心率/海拔联动图。
4. 实现范围查询与周/月趋势图。
5. 加入热力图、心率漂移、训练负荷和路线对比。
6. 在静态 JSON 已稳定后，再按需要用 FastAPI 提供查询接口；出现多用户或复杂持久化需求时再考虑数据库和 Spring Boot。

## 8. 第一版验收标准

第一版完成时，应能在浏览器中完成以下操作：

1. 在日历中看到每天的跑步量，并点击某日查看活动。
2. 在活动列表中按日期和距离筛选。
3. 打开任意一次含 GPS 的跑步，查看地图轨迹、起终点、距离、时长、心率和配速。
4. 移动时间/距离滑块时，地图位置与图表提示同步变化。
5. 选择一个日期范围，得到总距离、总时长、次数及每日/每周趋势。

## 9. 当前实现状态（2026-08-06）

第一版验收标准已经全部实现，并在此基础上完成了部分 P1 分析能力：

- 训练总览：按月切换的运动日历、每日里程趋势、月度统计和当月活动。
- 活动档案：日期、类型、最小距离和 GPS 状态筛选，支持分页和详情查看。
- 活动详情：Leaflet 轨迹、公里标记、回放滑块，以及配速、心率、海拔、功率和跑姿图表。
- 地图/图表联动：拖动地图回放滑块会同步所有图表提示；悬停任意图表会反向定位地图。
- 范围分析：30/90/180/365 天预设和自定义日期范围，总里程、时长、次数、爬升、整体配速及周趋势。
- 训练负荷：基于个人时长与平均心率的 7/28 日滚动负荷，并给出恢复、稳定、上升或增量较快提示。
- 单次洞察：配速变异系数、前后半程心率效率漂移、低速占比、自动训练类型和公里分段数据。
- 地图探索：由 567 条 GPS 轨迹预计算得到 851 个 250 米网格，支持日期、频次筛选、高频区域聚焦和全部范围查看。
- 视觉与交互：浅色、深色和跟随系统主题；iOS 18 风格毛玻璃；桌面单屏工作区与窄屏响应式布局。

